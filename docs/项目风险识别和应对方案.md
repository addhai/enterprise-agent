## 0. 文档目的

本文档对 enterprise-agent 项目在**交付、运行、安全、运维**四个维度进行风险识别，给出每个风险的**根因、概率/影响评分、预防措施（事前）与应急方案（事后）**，并定义风险监控与复盘机制。

> 定位提醒：本项目是**个人作品集**，目标是「生产级标准、面试可辩护、真实落地」。因此风险处置遵循两条硬约束：
> 1. **安全红线优先于展示力**——真实密钥（LLM key / 阿里云 AK / JWT secret）永不上公网、永不暴露。
> 2. **讲诚信、三态标注**——已实现 / 架构就绪 / 演示级，绝不把「样本兜底」说成「真实全通」。

## 1. 风险评分方法

采用 **风险值 = 可能性(L) × 影响(I)**，L、I 各取 1–5：

| 等级 | 风险值区间 | 含义 | 处置要求 |
|------|-----------|------|----------|
| 🔴 严重 (Critical) | 16–25 | 一旦发生将危及项目存续 / 泄露密钥 / 数据跨租户 | 必须立即有预防措施 + 应急脚本 |
| 🟠 高 (High) | 10–15 | 核心链路降级或演示失实，影响作品集可信度 | 需预防措施，定期验证 |
| 🟡 中 (Medium) | 5–9 | 局部功能受限或交付效率受损 | 有缓解手段即可 |
| 🟢 低 (Low) | 1–4 | 影响轻微、易恢复 | 记录观察 |

## 3. 详细应对方案

### A. 安全与合规（最高优先级）

#### A1 真实密钥误提交到公开 GitHub 仓库  🔴 严重
- **根因**：本地 `.env` / `.jwt_secret` 持有 LLM key / 阿里云 AK / JWT secret；git 铁律只 add 指定文件，但人为失误仍可能 `git add .` 或误 add `.env`。
- **预防**：
  - `.env`、`.jwt_secret` 已在 `.gitignore`；提交前 `git status` 复核，绝不 `git add .`。
  - CI 的 SAST job 增加密钥扫描（git-secrets / trufflehog / gitleaks），命中即 fail。
  - 对外一律使用**额度极小、可吊销的 demo 子 key**，不为展示申请高权限 AK。
- **应急**：一旦发现泄露——立即吊销对应 AK / LLM key；rotate JWT secret；`git filter-repo` 清理历史并提交；在仓库 Security 处吊销。
- **Owner**：拾一（提交纪律）+ 八弟（CI 扫描兜底）。

#### A2 公网 live demo 携带真实 key  🔴 严重
- **根因**：为追求展示力可能想把服务挂公网。
- **预防**：安全红线已拍板——任何携带真实 key 的公网 live demo 一律取消；只用本地 `docker` / `localhost` 或 demo 子 key 展示。
- **应急**：发现公网暴露立即下线并吊销密钥。
- **Owner**：拾一（决策红线）。

#### A3 多租户 tenant_id 隔离失效  🔴 严重
- **根因**：新增接口忘记带 `tenant_id` 过滤，导致跨租户读取。
- **预防**：已完成 `多租户-RBAC隔离核查.md`；用中间件强制注入 `tenant_id`；为跨租户查询写回归测试；API 层对写操作加 `tenant_id` 断言。
- **应急**：回归测试 + 数据分区审计；定位越权接口补过滤。
- **Owner**：八弟（测试）+ 拾一（评审）。

#### A4 RBAC 权限点越权  🟡 中
- **根因**：4 角色 + 权限点 + REST 管理 + seed 已实现，但权限中间件漏校验新端点。
- **预防**：统一权限中间件；新端点默认拒绝（deny-by-default）；seed 脚本可复现。
- **应急**：补中间件校验，回滚越权操作。
- **Owner**：八弟。

### B. 架构与技术

#### B1 Milvus 内存集成卡点  🔴 严重
- **根因**：沙箱无 docker daemon，Milvus 内存模式未跑通，向量库集成受阻。
- **预防**：现状以 `VECTOR_STORE_BACKEND=chroma` 稳定兜底；本机 docker 跑通 Milvus 后再切；保留 Chroma 作为永久降级后端。
- **应急**：向量检索回退 Chroma，不影响主链路；不强依赖 Milvus 内存模式。
- **Owner**：拾一（本机验证）+ 八弟。

#### B2 PostgreSQL 不可达 → SQLite 回退数据不一致  🟠 高
- **根因**：数据层单实例，PG 容器崩溃时 `STORAGE_BACKEND=auto` 回退 SQLite `./agent.db`，二者 schema/数据不互通。
- **预防**：生产必须 PG；监控 PG 健康；做好持久化卷 + 定期备份；明确「回退态 ≠ 生产态」。
- **应急**：重启 PG 容器并从备份恢复；回退态仅作本地演示。
- **Owner**：八弟（备份脚本）+ 拾一。

#### B3 Orchestrator 超时 / A2A 慢调用全超时  🟡 中
- **根因**：客服 Agent 调 LLM 慢，默认 30s 不够，曾 3 次重试全超时（已修为 120s 高超时 client）。
- **预防**：委托调用传入高超时 httpx client；限制重试次数；加熔断与降级回复。
- **应急**：LLM 慢时返回「稍后重试」兜底话术，不阻塞主流程。
- **Owner**：八弟。

#### B4 WebSocket 聊天主链路不稳定  🟠 高
- **根因**：`/ws/chat` 长连接，弱网 / 无头浏览器易断；本机验证须用 `localhost`（IPv6）而非 `127.0.0.1`。
- **预防**：WS 活跃连接 gauge 已埋点；前端加重连机制；vite 监听 IPv6 `localhost`。
- **应急**：断线自动重连 + 消息补偿；无头验证先注入 WS 拦截桩（见 HANDOFF 坑 4）。
- **Owner**：八弟。

#### B5 LangGraph Agent「演戏」未真执行工具  🟠 高
- **根因**：prompt 写死纯文本 ReAct（`Question:/Thought:/Action:`）与 LangChain 原生函数调用冲突，`tool_calls` 为空，模型纯文本「演」出执行结果。
- **预防**：prompt 改为函数调用友好格式；验证配方——打印 `intermediate_steps`，断言 `tool_calls` 非空。
- **应急**：交叉读存储确认落库；为空则判定为「未真执行」，返回「工具暂不可用」。
- **Owner**：八弟（调试配方已形成）。

#### B6 数据层单点故障（PG/Redis 单实例）  🟠 高
- **根因**：部署规格 api/ws `replicas=2`，但 PG/Redis 单实例，挂掉则全站不可用。
- **预防**：本机做好持久化卷 + 备份 + 健康检查；生产环境应上托管冗余版（如阿里云 RDS）。
- **应急**：单实例挂掉重启容器 + 挂载恢复卷。
- **Owner**：拾一（生产选型决策）。

### C. 数据与质量

#### C1 云资源真实性受阻（key + 付费）  🟠 高
- **根因**：`ALIYUN_DEMO_FALLBACK=true` 走样本兜底；翻真需真实子账号 AK + 付费。
- **预防**：`FallbackProvider` 真实优先、空才回退；`/api/v1/health` 暴露 `aliyun_demo_fallback` 标记**透明告知**当前是 demo 态。
- **应急**：申请额度极小、可吊销的 demo 子 key 翻真；或明确标注「演示态」不冒充真实。
- **Owner**：拾一（付费决策）+ 八弟。

#### C2 RAG 检索质量 / 幻觉  🟡 中
- **根因**：混合检索（BM25 + RRF + BGE-reranker / gte-rerank）仍可能召回不准。
- **预防**：命中分数阈值过滤；evaluate 测试覆盖；低置信度转人工。
- **应急**：低分答案标注「仅供参考」或转人工坐席。
- **Owner**：八弟。

### D. 交付与过程

#### D1 单人维护 / 知识集中  🔴 严重
- **根因**：个人项目，大三，自述计算机小白，唯一维护者，bus factor = 1。
- **预防**：持续维护 `HANDOFF.md` + 项目记忆 + 需求/架构文档；关键流程脚本化（verify_*.py）；每次收口更新交接文档。
- **应急**：文档即保险——接手人按 HANDOFF 可零上下文恢复；关键操作留可重跑脚本。
- **Owner**：八弟（文档）+ 拾一（确认）。

#### D2 GitHub push 频繁 Connection reset  🔴 严重
- **根因**：代理网络访问 GitHub 不稳，push 常 `Connection reset`。
- **预防**：本地先 `commit` 再分批 `push`；用 `gh` token 临时 remote URL 兜底（已验证可用）；失败重试而非 `--force`。
- **应急**：换网络 / 代理；或改走 `gh` 而非 GCM 凭据。
- **Owner**：拾一。

#### D3 覆盖率门禁低 + 关键路径无集成测试  🟡 中
- **根因**：CI 覆盖率门禁 40%（裸环境 ~47.8%）偏低；沙箱无 docker，全栈集成测试 `verify_fullstack.py` 未跑。
- **预防**：提升关键路径（鉴权、租户隔离、RAG、WS）单测；本机跑 `verify_fullstack.py` / `verify_monitoring.py` 补集成验证。
- **应急**：应用层本地实测已通过（`verify_fullstack_local.py` EXIT=0），缩小盲区。
- **Owner**：八弟。

#### D4 并行编辑同一文件修改丢失  🟡 中
- **根因**：多子代理并行编辑同一文件，基于旧快照覆盖。
- **预防**：避免多代理同文件并行编辑；修改后用 Read 验证所有改动。
- **应急**：`git diff` 找回丢失改动。
- **Owner**：八弟（编排纪律）。

### E. 运维与部署

#### E1 全栈 Docker 联调本地未真跑  🟠 高
- **根因**：三段式验证第②③步（docker 版全栈 + Grafana 渲染）待你本机执行，沙箱无 daemon。
- **预防**：本机 `docker-compose up` + `scripts/verify_fullstack.py` + `scripts/verify_monitoring.py` 全套跑通。
- **应急**：应用层本地实测已通过，盲区仅在 docker / 监控渲染，风险可控。
- **Owner**：拾一（本机执行）。

#### E2 监控管线渲染未验证  🟡 中
- **根因**：沙箱无浏览器/docker，Grafana dashboard（PromQL、datasource uid）未端到端渲染验证。
- **预防**：`verify_monitoring.py` 本机跑；dashboard 已修 PromQL + `datasource uid=prometheus`。
- **应急**：手动核对 `/api/v1/metrics/prometheus` 出数。
- **Owner**：拾一。

#### E3 阿里云真实 API 调用产生费用  🟡 中
- **根因**：翻真需真实 AK，调用计费（与红线「付费前先问」冲突）。
- **预防**：任何付费操作先问拾一确认；默认 sample 兜底；申请子 key 设额度上限 + 预算告警。
- **应急**：超预算立即停用 AK。
- **Owner**：拾一（决策）。

### F. 范围与产品

#### F1 范围蔓延 / 过度工程 vs 生产级  🟡 中
- **根因**：用户要「生产级」易滑向 gold-plating，超出 MVP 红线。
- **预防**：严守 MVP 4 条红线（形态 / 数据真实 / 多租户+RBAC / 容器多副本）；按三态标注讲诚信。
- **应急**：新需求先入表评估，不临时加塞。
- **Owner**：八弟（PM 控范围）+ 拾一。

#### F2 演示态 vs 真实态混淆，作品集可辩护性受损  🟠 高
- **根因**：demo fallback 让展示看起来「全通」，实际部分走样本兜底，面试易被追问击穿。
- **预防**：文档三态标注（已实现/架构就绪/演示级）；`health` 暴露 `aliyun_demo_fallback`；面试讲清真/假边界。
- **应急**：准备真实集成证据链（真实 AK 跑通截图 / 日志）。
- **Owner**：八弟（标注）+ 拾一（答辩准备）。

## 5. 风险监控与复盘机制

| 机制 | 触发条件 | 责任方 | 节奏 |
|------|----------|--------|------|
| 密钥扫描 | 每次 push / PR | CI SAST job | 实时 |
| 三段式验证 | 每次收口 / 发布前 | 拾一（本机） | 每次大改 |
| HANDOFF 更新 | 每次会话结束 | 八弟 | 每会话 |
| 风险复审 | 新增重大功能 / 架构变更 | 八弟 + 拾一 | 月度 |
| 红线复核 | 任何公网 / 密钥相关操作前 | 拾一 | 即时 |

**复盘原则**：严重级（🔴）风险必须「预防措施 + 应急脚本」双齐全；高等级（🟠）风险需定期本机验证闭环；中/低级记录观察即可。

## 6. 红线重申（最高优先级）

1. 真实密钥（LLM key / 阿里云 AK / JWT secret）**永不上公网、永不暴露**。
2. 任何公网带真实 key 的 live demo **一律取消**。
3. 对外展示只用本地 `docker` / `localhost` 或**额度极小、可吊销的 demo 子 key**。
4. 任何**付费**操作（真实云 API 调用等）**先问拾一确认**。

## 7. 密钥泄露应急手册（对应 A1 应急）

一旦怀疑真实密钥（LLM key / 阿里云 AK / JWT secret）已泄露到公开仓库或公网，按以下顺序执行：

1. **立即吊销**：阿里云 RAM 控制台吊销对应子账号 AK；LLM 平台吊销/轮转 API key；JWT 用新随机串重新生成 `.jwt_secret`。
2. **清理历史**：`git filter-repo --path .env --invalidate-refs`（或 BFG）清除库中残留，并 `git push --force` 更新远程（force push 前先与协作者同步，避免覆盖他人进度）。
3. **平台侧吊销**：GitHub → Settings → Developer settings / Security 处吊销相关 token，检查 Authorization 日志有无异常调用。
4. **复盘**：更新本方案，记录泄露路径（是 `git add .` 还是写进代码），补强对应预防项。

> 红线优先级最高：真实密钥永不上公网、永不暴露；对外展示只用本地 docker/localhost 或额度极小可吊销的 demo 子 key。
