## 1. 系统定位与本计划的边界

系统服务于工厂内网场景，面向一线设备运维与工艺人员，回答工业手册、SOP、图纸说明中的检索与问答需求。三条不可动摇的约束决定了所有技术选型：

1. 运行时零外网依赖，模型全部本地推理（Ollama qwen2.5:7b，CPU）。
2. 工业手册引用是安全责任级溯源，答案必须能回到具体文档与页码。
3. 单台 x86 服务器部署，8 个容器共存（app / ollama / chroma / postgres / redis / prometheus / grafana / node-exporter / cadvisor），算力无弹性扩容空间。

本计划只覆盖「现有架构的增量加固」，不包含平台化重写、多集群、GPU 采购等大版本议题。任何阶段引入新组件，都必须先回答两个问题：离线部署增加多少维护面，CPU 预算从哪里让渡。

### 2.3 Q3 页码链路修复内容（2026-10-07 代码已完成）

- `src/rag/chunker.py` 新增 `expand_pdf_pages()`：切块前按 PAGE-BREAK 把 PDF 文档展开为物理页级 Document，盖 `metadata["page"]`（int，从 1 起），标准粒度与句子粒度两路径统一走该函数；无 PAGE-BREAK 的非 PDF 文档原样透传，不产生 page 键（Chroma 不接受 None 值）。
- `src/rag/outline.py` `OutlineTree.split()` 在 PDF 章节切片时写入内部键 `_page_offset`（本章首页相对文档首页的物理页偏移），展开后由 chunker 弹出，不透传到检索层。没有这一层，每章页码都会从 1 重新计数。
- `src/websocket/routes.py` `_build_citations()` 输出新增 `page` 字段，int 安全转型，非 PDF 语料为 null。
- `frontend/src/App.tsx` 的 `ChatCitation` 接口新增 `page?: number | null`，引用卡片标题区渲染「第 N 页」徽标（CSS 类 `chat-citation-page`，`App.css`），page 缺省时不占位。
- 测试：`tests/test_chunker_units.py` 新增 6 个页码用例（透传、编号、空页、章节偏移、两粒度盖戳），`tests/test_websocket/test_routes_logic.py` 新增 2 个引用透出用例。
- 前端构建产物 `static/assets/` 已核验含 `chat-citation-page`，oxlint 0 error，Playwright 6/6 通过。

**页码语义的诚实边界**：当前 page 是 PDF 物理页序。页眉印刷页码与物理页序的映射（loader 已有 `page_numbers` 文档级元数据）留待阶段 2 增强，物理页序在现阶段已是可核对的溯源信息。

**生效状态（2026-10-07 深夜已完成）**：经授权执行两轮 `scripts/rebuild_index.py` 与 app 容器重建（镜像 9cbef989），生产索引 PDF 块 100% 带物理页戳，WS 引用实测显示第 5/6 页。实施中额外修复两处：章节单页场景的 `_page_offset` 泄漏、`scripts/start-app.sh` CRLF 导致的容器启动失败。详见 CURRENT.md 同日区块。

## 3. 总体目标

| 维度 | Q4 结束时的目标 |
|---|---|
| 可信 | 每条带引用的回答可回到文档与物理页码；50 题金标题库上，检索命中率与答案正确率有量化基线且可回归 |
| 可交付 | master 随时可发版，CI 五 job 持续全绿，发版动作有脚本化 smoke 与回滚预案，不依赖个人记忆 |

演进原则按优先级排序：先还债再扩能，先测量再优化，先脚本化再自动化，先内网约束再谈体验。

## 5. 阶段 1：质量闭环（W42 - W44，10/13 - 11/02）

目标：质量从「抽样感觉还行」变成「有题库、有基线、能回归」。

### 5.1 五十题金标题库

- 从真实工业语料按难度分层抽题：事实定位（含页码核对）20 题、跨章节综合 15 题、操作流程 10 题、拒答与越界 5 题。每题记录标准文档、标准页码、参考答案要点。
- 题库存为版本化数据文件（建议 `tests/golden/questions.yaml` 或同级目录），人工评审一次后冻结，后续只增不改，防止题库向模型行为漂移。
- 自动判分拆两层：检索层判命中文档与页码（可全自动），答案层判要点覆盖（先人工打分跑通流程，再评估上 LLM 裁判的成本与偏差）。

### 5.2 真实链路 E2E

- 现有 Playwright 6 用例全部 mock 后端，保证不了后端质量。补一条在测试环境打真实 app + 本地 Ollama 的问答链路用例，允许慢，单独打标记不进快速 CI，进 nightly。
- 首 token 延迟在本轮必须测出真实数字，填进 `docs/PERFORMANCE_BASELINE.md` 的空表，消灭「零实测」指标。

### 5.3 工程还债

| 项 | 当前 | 目标 |
|---|---|---|
| 覆盖率门禁 fail_under | 40（`pyproject.toml`） | 55，随题库 PR 分两次抬升（48 → 55），不搞一次性跳变 |
| loader 单测 | docx 10% / image 14% / text 19% / html 23% | 四个 loader 均 ≥ 70%，按真实语料样本构造夹具 |
| 匿名 WS 会话 | 匿名会话被租户过滤成 0 文档（CURRENT.md 待办 #2），行为对用户不可解释 | 产品决策二选一并落地：匿名只读公共知识库，或匿名直接引导登录；决策前先补一条测试复现现状 |
| chapter_path | 索引里有该键，`src/websocket/routes.py` 0 处透出 | 评估在阶段 1 末尾随引用结构一起透出，前端展示章节面包屑 |

阶段 1 验收：金标题库首跑分数字入档（命中率、页码准确率、答案要点覆盖率、P50/P95 延迟、拒答正确率），五项全部有基线值，哪怕数字难看。难看的基线价值远高于没有基线。

## 6. 阶段 2：体验与容量（W45 - W48，11/03 - 11/30）

目标：在单机算力天花板内，把「能答对」推进到「答得快、排得上、定位细」。

| 任务 | 动机与做法 | 验收 |
|---|---|---|
| 6.1 模型选型对比 | qwen2.5:7b 直答 130s 起步是体验最大瓶颈。同题跑 3B 量化版与 7b，记录首 token、总耗时、金标题库质量三组数据 | 数据驱动决策，质量回退超过预设阈值（建议答案要点覆盖降 > 8 个百分点）则不换 |
| 6.2 排队替代 BUSY | 单 worker 的 WS BUSY 语义下第二个人直接被拒。引入轻量任务队列（Redis 已有），前端显示排队位置与预计等待 | 并发 5 会话压测下无硬拒绝，排队语义有超时与放弃处理 |
| 6.3 印刷页码映射 | 利用 loader 已有的 `page_numbers`，把物理页序映射为手册印刷页码，前端展示以印刷页为准、物理页为副 | 抽样 3 本手册人工核对 20 页映射正确 |
| 6.4 chapter_path 透出 | 若阶段 1 未做则在此闭环，引用展示「文档 > 章节」路径 | WS citations 含 chapter_path 并有单测 |
| 6.5 MCP/工具瘦身 | ReAct 400s 以上的耗时很大部分在工具选择与无效调用。按金标题库统计各工具真实调用率，裁剪或合并低频工具 | 平均工具调用轮次下降，ReAct 总耗时下降，质量指标不回退 |

辩证提醒：排队与 3B 都在改善「等待体验」，但单机算力总量没变，排队只是把拒绝变成等待。若上线并发真实超过 18 题/小时，硬件扩容是唯一根本解，本阶段所有软件优化都应在文档中明确这一边界。

## 7. 阶段 3：运营化（W49 - W52，12/01 - 12/28）

目标：系统从交付项目变成可运营产品，质量由数据说话。

1. PG 问答看板：把 answer_path、检索命中文档、RRF/rerank 分数、延迟、用户反馈写入 Postgres，Grafana 出三块面板（质量分布、延迟分布、无答案问题 Top N）。无答案问题清单直接反哺语料补录。
2. 阈值再标定：用一个月真实问答分布，重新标定 RRF k 值、rerank 截断数、相似度拒答阈值，每次调整必须有金标题库回归对照，禁止线上裸调。
3. UAT 与 SLO：与车间用户做两轮 UAT，把「直答 P95 延迟」「页码准确率」「拒答正确率」写成内部 SLO 数字并指定责任人。
4. 文档降漂：本仓库 docs/ 已积累大量阶段性文档（Phase2、Phase3、各次 hot reload 记录），阶段 3 末做一次归档，现行有效文档进索引，过期文档进 `docs/archive/`，降低新人读文档的信噪比。

## 8. 风险与回滚

| 风险 | 影响 | 缓解与回滚 |
|---|---|---|
| 索引重建后检索质量异常 | 线上问答质量下降 | 重建前备份 Chroma 卷；重建后先跑金标题库抽样再切流量；回滚直接恢复卷备份（卷内已有 `chroma_pre_rebuild_20261006.tar.gz`） |
| chunker 改动影响非 PDF 语料 | md 等语料切块行为变化 | `expand_pdf_pages()` 对无 PAGE-BREAK 文档原样透传，并有单测锁定；代码回滚点集中在 `chunker.py` 单函数 |
| 模型降级（7b → 3B）质量回退 | 答案正确率下降 | 只在金标题库 A/B 达标后切换；镜像双 tag 保留，compose 切环境变量即可回退 |
| CPU 资源争用（队列堆积、监控抓取） | 尾延迟恶化 | 队列长度设硬上限并走明确拒答；Prometheus 抓取间隔在阶段 2 压测后复核 |
| 覆盖率门禁抬升阻塞日常 PR | 交付速度下降 | 两次分步抬升，新代码门禁与存量债分开，不追旧账 |
