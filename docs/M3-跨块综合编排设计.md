# M3 跨块综合专用编排设计（草案，待批准）

创建：2026-10-09
状态：待批准，不写生产代码
基线：M2 prompt v1，全量 39/50 pass（报告 scripts/golden/reports_prompt_v1_full/）

## 1. 要解决的问题

M2 收口后剩余 3 个稳定失败的库内题，探针实证资料全部在注入上下文中，
失败发生在「多块资料 → 单一答案」的综合环节。

| 题号 | 现象 | 缺失 | 根因 |
|------|------|------|------|
| GS02 | 只答 F02 处理步骤 | 保修 12 个月、8 个月在保 | 故障块与保修块跨域，模型抓住一块丢一块 |
| GS01 | 答对 550℃/50:1 数值 | 「参数冲突以规格说明书为准」裁决规则 | 数字块压过元规则块 |
| GP06 | 答对退货与运费承担 | 7 天期限未引述 | 期限事实被流程事实淹没 |

共同模式：问题含 2 个以上提问点或需要 2 个以上资料块桥接时，
7B 模型在 5 块拼接上下文（每块 1500 字）中只对最显著的一块作答，
支撑性事实（期限、裁决依据、保修状态）系统性丢失。

## 2. 问题本质

这是单轮生成的注意力分配问题，不是检索召回问题。
继续加 rerank、加 top_k、改切块都无法保证模型「注视」每一块。
需要用编排手段把「逐块扫描」从模型的自觉行为变成强制流程。

约束条件：

- 纯 CPU、qwen2.5:7b 实测 3.6 tok/s，每题已 150~230s，新增 LLM 调用极贵
- 小模型对输出格式的遵从度高于对行为准则的遵从度
- 金标题库 frozen，判据以关键词组出现为准，任何改动需全量回归防退化

## 3. 方案对比

### 方案 A：单生成内标签化综合（零额外调用）

一次 LLM 生成中强制输出两段结构，服务端剥离分析段只外发答案段：

```
<coverage>
提问点：① ... ② ... ③ ...
逐块要点：
- 文档1：与①相关的事实...
- 文档3：与②相关的事实...
覆盖表：①←文档1 ②←文档3+文档4 ③无资料
</coverage>
<answer>
给用户的最终答案
</answer>
```

收益：逐块注视被格式强制执行；覆盖表让「无资料的提问点」显式化，
抑制漏问；零额外调用。
代价：输出增加约 300~500 token，单题预计 +20~60s；
依赖模型遵守标签格式，需有格式失败降级。

### 方案 B：map-reduce 两阶段（备选，不首选）

每块一次提取调用（5 次）+ 一次综合调用，共约 6 次串行推理。
质量最确定，但 CPU 下单题增加 3~5 分钟，大概率整体冲破 600s 墙。
仅在方案 A 金标证伪后启用，且以前置 ollama 双模型驻留优化落地为条件。

### 方案 C：提问点信号保底注入（零调用，检索侧）

问题含「保修/保内/期限/几天/为准/冲突」等信号词时，
把含对应事实但被 rerank 挤出 top_k 的块保底补入注入列表。

收益：毫秒级，给 GS 类问题上双保险。
局限：只解决排序，料已在上下文仍被无视的场景（GS02 现状）无帮助。

### 结论

A + C 组合先行，同开关控制；B 列为方案 A 证伪后的备选。
两部分均可通过环境变量秒级关回 M2 prompt v1 行为。

## 4. 选定方案的数据流转

```
用户问题
  │
  ├─ 检索（现有：vector + BM25 + sentence → RRF → rerank → top5）
  │
  ├─【C】提问点信号检测（规则，src/rag 或 src/graph 新增纯函数）
  │     信号词命中 → 从落选候选中保底补入对应块（最多补 1~2 块，硬上限）
  │
  ├─ 上下文组装（现有 _format_pre_retrieved_context）
  │     [文档1]..[文档N] 编号保留，供 coverage 引用
  │
  ├─【A】综合 prompt（仅高置信直答路径 _DIRECT_ANSWER_SYSTEM_PROMPT 改造）
  │     要求固定输出 <coverage> + <answer> 两段
  │
  ├─ LLM 单次生成
  │
  ├─【后处理】标签提取（新增纯函数 + 确定性单测）
  │     命中 <answer> → 取其内容作 final_response
  │     <coverage> → 落日志/trace，不发给用户
  │     无标签或标签残缺 → 降级用全文，记 warning，不阻断
  │
  └─ 现有 reply 组装、安全闸门、引用计数
```

边界约定：

- 首批只改直答路径（生产 kb_call_mode=always 的主路径），ReAct 路径不动，
  避免一次动两条链路归因困难
- coverage 中禁止出现具体虚构事实，只允许引用文档编号与原文事实
  （M2 few-shot 证伪教训：7B 会照抄示例虚构值，故格式示例只用占位符）
- llm_max_tokens 现为 2048，coverage+answer 预算够，不调大
- 引用计数仍按现有口径从 page_content 匹配，coverage 剥离不影响引用

## 6. 开关与回退

- SYNTHESIS_ENABLED=false 时：prompt 用 M2 原文、信号保底不执行、
  后处理直通，行为与当前生产逐字节一致
- 金标回归负向：env 关回，无需回滚镜像；热部署同理

## 7. 测试与验收计划

1. 确定性单测：标签正常提取、残缺标签降级、多 answer 标签取首段、
   信号词→保底块映射、保底不超硬上限
2. 全量 50 题金标回归（真机，ollama 双驻留档位）：
   - GS01/GS02/GP06 至少救回 2 题，且关键词缺失组清零或明确归因
   - 总通过数不低于 39/50（防退化红线）
   - p50 延迟增幅 ≤20%，无新增 600s 超时
3. 抽样人工检查 5 题答案，确认 coverage 未泄露给用户、无编号元信息外泄
4. 关开关复跑 3 题，确认行为回到 M2 基线

## 8. 风险（辩证）

- 7B 不遵守标签：降级路径保证不崩，但质量收益归零，靠金标判定
- coverage 成为新幻觉来源：禁止具体事实示例、只引编号，仍需人评抽查
- 信号保底引入不相关块挤占上下文：硬上限 1~2 块且金标全量回归兜底
- 输出变长加剧提前收尾风险：answer 段规则沿用 M2 完整性条款，
  coverage 在 answer 之前生成反而先完成「扫描」，预期缓解收尾问题，实测验证

## 9. 真机实测迭代（2026-10-09）：二级门控定型

两轮全量 50 题 A/B 对照（A：M2 提示词加检索修复，B：M3 全量启用，
其余环境完全一致）后的结论与定型形态。

### 9.1 全量启用的实测问题

- B 轮 38/50 对 A 轮 35/50，净 +3，但 p50 132.7s 升到 175.2s（+32%，
  越过 ≤20% 红线），并出现 1 例 600s 硬超时（GS14）
- 救回题答案目标长度 50 到 150 字（周期档位、参数冲突裁决、在保判定）
- 翻车题答案目标长度 250 到 330 字（步骤、清单、禁忌枚举）。实证：
  GP01 答案由 A 轮 328 字 pass 退化为 B 轮 232 字 fail，GS14 打满
  600s。coverage 分析段在 2048 token 预算内挤占长答案，注意力也被分流
- 7B 标签遵从性：约三成题漏闭合标签，剥离函数已实现四级容错，
  50 题零标签残骸外泄，遵从性问题不影响安全性只影响收益稳定性

### 9.2 定型：逐题二级门控 should_use_synthesis

总开关 synthesis_enabled 之外增加逐题判定，同时满足才走 coverage：

1. 注入资料 distinct source 至少 2 个（同一 PDF 多 chunk 是切片不是跨块）
2. 问题不含长流程引导词（步骤、流程、清单、规程、怎么操作、如何操作、
   操作顺序、前几步）

50 题离线回放：coverage 组 29 题对 M2 净救回 4 题（GF02/GF13/GF14/GS01）、
零新挂；流程组与单来源组 21 题保持 M2 行为（GP01 恢复 328 字 pass、
GS14 不再撞 600s）。门控后预期总分 39/50，混合 p50 156s（对 A +18%）。

### 9.3 同期修复的链路缺陷（非 M3 逻辑本身）

- WS 间歇零帧断连（约 4% 到 9% 概率随机换人）：LLM 200 正常返回同秒
  连接被 Docker Desktop WSL2 端口转发静默回收。uvicorn 心跳由
  300/300 收紧为 25/60，客户端评测关闭 ping
- session_manager 在 90s 心跳阈值误清理在途长推理会话：新增
  workflow_active 在途标记豁免，3600s 绝对兜底防标记泄漏
- ollama 双模型驻留内存越线：FLASH_ATTENTION 加 KV q8 量化，
  匿名内存稳态 9.5G 降到 6.9G，热态 GF05 243s 降到 21.6s
